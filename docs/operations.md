# اجرای «لولو» روی سرور (مرجع عملیات)

این سند مرجع کوتاه اجرای production است: اجزا، تنظیمات، HTTPS با Caddy، سرویس‌ها، به‌روزرسانی، بکاپ و عیب‌یابی.

- **راه‌اندازی از صفر:** اگر اولین بار است سرور را آماده می‌کنید، راهنمای قدم‌به‌قدم `docs/server-setup.md` را دنبال کنید؛ این سند جزئیات پشت آن را دارد.
- **بکاپ:** `docs/backup.md`.
- **کار با پنل و ورود:** `docs/panel.md`.

## ۱. اجزا

```
اینترنت ──HTTPS (۴۴۳)──► Caddy
                          ├─ /telegram/webhook ──► ربات   (127.0.0.1:8443)
                          └─ بقیه (پنل و ‎/api)  ──► API    (127.0.0.1:3000)

ربات، worker و API ──► PostgreSQL در داکر (127.0.0.1:5432)
worker ──► api.telegram.org  (ارسال پیام‌ها، با رعایت محدودیت نرخ)
```

| بخش        | چه می‌کند                                                                                        | اجرا                                 |
| ---------- | ------------------------------------------------------------------------------------------------ | ------------------------------------ |
| ربات       | پیام‌ها و دکمه‌های تلگرام را از webhook می‌گیرد و نتیجه را در صف ارسال می‌نویسد                  | سرویس `lulu-bot`                     |
| worker     | صف ارسال را به تلگرام می‌فرستد؛ تسویهٔ دوره‌ای، فعال کردن بستهٔ روح شب و پاک‌سازی را اجرا می‌کند | سرویس `lulu-worker`                  |
| API و پنل  | پنل مدیریت و API آن، روی یک آدرس                                                                 | سرویس `lulu-api`                     |
| PostgreSQL | همهٔ داده؛ تنها سرویس پشتیبان لازم (Redis لازم نیست)                                             | `docker compose`، کانتینر `postgres` |
| Caddy      | HTTPS با گواهی خودکار Let's Encrypt، و رساندن درخواست‌ها به ربات و API                           | سرویس `caddy`                        |

- هر سه برنامه هنگام روشن شدن **migrationهای دیتابیس را خودکار اعمال می‌کنند**. اگر چند تا با هم روشن شوند، با قفل دیتابیس پشت سر هم اجرا می‌شوند.
- ربات، worker و API فقط روی `127.0.0.1` گوش می‌دهند. از بیرون فقط پورت‌های ۸۰ و ۴۴۳ (Caddy) و ۲۲ (SSH) باز است.
- **یک توکن، یک ربات:** با هر توکن فقط یک ربات می‌تواند روشن باشد. وقتی ربات سرور روشن می‌شود، webhook را ثبت می‌کند و رباتی که با همان توکن جای دیگری در حالت polling روشن است دیگر پیامی نمی‌گیرد. پیش از روشن کردن سرور، ربات سیستم دیگر را خاموش کنید.

## ۲. تنظیمات (`.env`)

فایل `/srv/lulu/.env` را `deploy/make-env.sh` با رمزهای تصادفی تازه می‌سازد. همهٔ سرویس‌ها و `docker compose` همین یک فایل را می‌خوانند. این فایل فقط برای صاحبش خواندنی است و هرگز در git نمی‌رود.

| متغیر                                                  | مقدار در سرور     | توضیح                                                             |
| ------------------------------------------------------ | ----------------- | ----------------------------------------------------------------- |
| `NODE_ENV`                                             | `production`      | در این حالت webhook و cookie امن اجباری‌اند                       |
| `POSTGRES_PASSWORD`، `DATABASE_URL`                    | رمز تصادفی hex    | رمز دیتابیس؛ در `DATABASE_URL` هم همان می‌آید                     |
| `TELEGRAM_BOT_TOKEN`                                   | توکن BotFather    | فقط همین‌جا؛ در لاگ نمی‌آید                                       |
| `TELEGRAM_MODE`                                        | `webhook`         |                                                                   |
| `PUBLIC_BASE_URL`                                      | `https://<دامنه>` | تلگرام به `<دامنه>/telegram/webhook` پیام می‌فرستد                |
| `TELEGRAM_WEBHOOK_SECRET`                              | رشتهٔ تصادفی hex  | تلگرام آن را در هر درخواست برمی‌گرداند؛ درخواست بدون آن رد می‌شود |
| `ADMIN_ORIGIN`                                         | `https://<دامنه>` | مبدأ مجاز پنل                                                     |
| `SESSION_SECRET`                                       | رشتهٔ تصادفی hex  | کلید امضای نشست و CSRF                                            |
| `COOKIE_SECURE`                                        | `true`            | cookie با پیشوند `__Host-` و فقط روی HTTPS                        |
| `API_TRUST_PROXY`                                      | `127.0.0.1`       | تا محدودیت تلاش ورود، IP واقعی کاربر را از Caddy ببیند            |
| `ADMIN_BOOTSTRAP_USERNAME`، `ADMIN_BOOTSTRAP_PASSWORD` | حساب مالک اول     | فقط `npm run admin:bootstrap` می‌خواند؛ بعد از ساخت حساب پاک شود  |
| `BACKUP_DIR`، `BACKUP_KEEP`                            | `backups`، `10`   | بکاپ‌هایی که از پنل گرفته می‌شود                                  |

اگر مقداری غلط باشد، سرویس روشن نمی‌شود و در لاگ **نام** متغیر و قاعده‌اش را می‌گوید، نه مقدارش را.

بعد از هر تغییر در `.env` سرویس‌ها را دوباره روشن کنید: `sudo systemctl restart lulu-api lulu-worker lulu-bot`.

## ۳. HTTPS با Caddy

فایل نمونه: `deploy/Caddyfile`. فقط نام دامنه را عوض کنید و در `/etc/caddy/Caddyfile` بگذارید.

```
lulu.example.com {
	encode zstd gzip
	handle /telegram/webhook {
		reverse_proxy 127.0.0.1:8443
	}
	handle {
		reverse_proxy 127.0.0.1:3000
	}
}
```

- **گواهی:** Caddy گواهی را خودش از Let's Encrypt می‌گیرد و پیش از انقضا تمدید می‌کند. شرط‌ها:
  - رکورد A دامنه به IP سرور اشاره کند؛
  - پورت‌های ۸۰ و ۴۴۳ باز باشند.
- **هدرهای امنیتی:** هدرهای امنیتی، CSP سخت‌گیر و HSTS را خود API می‌فرستد؛ در Caddy تنظیم جدا لازم نیست.
- **IP واقعی:** Caddy آدرس کاربر را در `X-Forwarded-For` می‌گذارد. API فقط به همین proxy محلی اعتماد می‌کند (`API_TRUST_PROXY=127.0.0.1`).
- **دستورها:**
  - بررسی فایل: `sudo caddy validate --config /etc/caddy/Caddyfile`
  - اعمال: `sudo systemctl reload caddy`
  - لاگ: `journalctl -u caddy -n 50`

## ۴. سرویس‌ها

فایل‌های `deploy/systemd/lulu-*.service` را در `/etc/systemd/system/` کپی کنید.

- هر سرویس با کاربر جدای `lulu` اجرا می‌شود و تنظیماتش را از `/srv/lulu/.env` می‌خواند.
- اگر سرویسی بیفتد، بعد از ۵ ثانیه خودش دوباره روشن می‌شود. بعد از ری‌استارت سرور هم خودکار روشن می‌شوند.
- PostgreSQL در داکر با `restart: unless-stopped` بعد از ری‌استارت سرور خودش برمی‌گردد.

| کار              | دستور                                                          |
| ---------------- | -------------------------------------------------------------- |
| وضعیت            | `systemctl status lulu-bot lulu-worker lulu-api`               |
| روشن کردن دوباره | `sudo systemctl restart lulu-api lulu-worker lulu-bot`         |
| خاموش کردن       | `sudo systemctl stop lulu-bot lulu-worker lulu-api`            |
| لاگ زنده         | `journalctl -u lulu-bot -f` (برای خروج: `Ctrl + C`)            |
| ۱۰۰ خط آخر لاگ   | `journalctl -u lulu-worker -n 100 --no-pager`                  |
| وضعیت دیتابیس    | `cd /srv/lulu && sudo docker compose ps`                       |
| سلامت API        | `curl -s https://<دامنه>/api/health` (باید `{"ok":true}` باشد) |

- **صفحهٔ «سیستم» در پنل:**
  - وضعیت ربات و worker (heartbeat هر ۳۰ ثانیه)؛
  - آخرین اجرای هر کار زمان‌بندی‌شده؛
  - پیام‌های ناموفق صف ارسال.

## ۵. به‌روزرسانی

```
sudo /srv/lulu/deploy/update.sh
```

اسکریپت به‌ترتیب این کارها را می‌کند:

1. بکاپ `pg_dump` از دیتابیس؛
2. `git pull`؛
3. `npm ci` و `npm run build`؛
4. روشن کردن دوبارهٔ سه سرویس. migrationهای تازه هنگام روشن شدن اعمال می‌شوند.

**برگشت به نسخهٔ قبل:**

- migrationها فقط جلو می‌روند. کد قدیمی‌تر لزوماً با دیتابیسِ migrate‌شده کار نمی‌کند.
- اگر به‌روزرسانی مشکل داشت:
  1. سرویس‌ها را خاموش کنید؛
  2. با `sudo -u lulu git -C /srv/lulu checkout <commit قبلی>` به کد قبل برگردید؛
  3. `npm ci` و `npm run build` را اجرا کنید؛
  4. دیتابیس را از بکاپی که همان اسکریپت پیش از به‌روزرسانی گرفت بازگردانید (`docs/backup.md`، بخش ۲)؛
  5. سرویس‌ها را روشن کنید.

## ۶. بکاپ خودکار

- **بکاپ شبانه:** فایل `/etc/cron.d/lulu-backup` هر شب یک `pg_dump` کامل در `/var/backups/lulu` می‌گیرد. ساعت ۲۳:۳۰ UTC، یعنی ۳ بامداد به وقت تهران.
  - هر فایل بعد از ساخته شدن خوانده و بررسی می‌شود؛
  - فایل‌های قدیمی‌تر از ۱۴ روز پاک می‌شوند؛
  - گزارش هر اجرا در `/var/log/lulu-backup.log` است.
- **نسخهٔ بیرون از سرور:** بکاپی که فقط روی همان دیسک است، با از دست رفتن سرور از بین می‌رود. دست‌کم هفته‌ای یک بار آخرین فایل را به کامپیوتر خودتان بیاورید (`docs/server-setup.md`، قدم ۱۵).
- **بازگردانی و تست بازگردانی:** `docs/backup.md`.

## ۷. آوردن دادهٔ رباتی که با `npm run dev` اجرا شده

اگر ربات تا حالا روی کامپیوتر دیگری با `npm run dev` کار می‌کرده و بازیکن‌ها همان داده را دارند، می‌توانید آن را به سرور بیاورید. این کار باید **پیش از ساخت حساب مالک** (`admin:bootstrap`) و **پیش از روشن کردن سرویس‌ها** انجام شود.

1. **روی همان کامپیوتر، در PowerShell، داخل پوشهٔ پروژه:**
   - `npm run dev` را روشن کنید تا دیتابیس محلی بالا بیاید.
   - در پنجرهٔ دوم PowerShell:

   ```powershell
   $pw = (Get-Content .lulu-dev\credentials.json | ConvertFrom-Json).password
   $env:DATABASE_URL = "postgres://lulu:$pw@127.0.0.1:54329/lulu_dev"
   npm run backup:create
   ```

   - اگر در `.env` آن کامپیوتر `DEV_DB_PORT` را عوض کرده‌اید، به‌جای `54329` همان را بگذارید.
   - فایل در پوشهٔ `backups` ساخته می‌شود، با نامی مثل `lulu-backup-20261015-120000Z.jsonl.gz`.

2. **ربات آن کامپیوتر را خاموش کنید** (`Ctrl + C`). از این لحظه پیام‌ها تا روشن شدن سرور جواب نمی‌گیرند. تلگرام پیام‌های تا ۲۴ ساعت را نگه می‌دارد.

3. **فایل را به سرور بفرستید:**

   ```powershell
   scp backups\lulu-backup-20261015-120000Z.jsonl.gz root@<IP>:/srv/lulu/backups/
   ```

4. **روی سرور بازگردانید:**

   ```
   sudo chown lulu:lulu /srv/lulu/backups/*.jsonl.gz
   cd /srv/lulu && sudo -u lulu -H npm run backup:restore -- backups/lulu-backup-20261015-120000Z.jsonl.gz
   ```

   اگر گفت دیتابیس داده دارد، یعنی سرویس‌ها یا `admin:bootstrap` قبلاً اجرا شده‌اند. وقتی مطمئن‌اید چیزی از سرور لازم نیست، `--replace` را اضافه کنید.

5. ادامهٔ راهنما (ساخت حساب مالک و روشن کردن سرویس‌ها) را دنبال کنید.

## ۸. چک‌لیست امنیت

- [ ] `.env` فقط برای `lulu` خواندنی است (`ls -l /srv/lulu/.env` → `-rw-------`) و دو خط `ADMIN_BOOTSTRAP_*` از آن پاک شده است.
- [ ] فایروال فقط ۲۲، ۸۰ و ۴۴۳ را باز گذاشته است (`sudo ufw status`).
- [ ] رمز root عوض شده است، یا ورود با کلید SSH است.
- [ ] بکاپ شبانه کار می‌کند (`tail /var/log/lulu-backup.log`) و نسخه‌ای بیرون از سرور هست.
- [ ] به‌روزرسانی‌های امنیتی اوبونتو خودکار نصب می‌شوند. در اوبونتو ۲۴.۰۴ به‌طور پیش‌فرض روشن است: `systemctl status unattended-upgrades`.
- [ ] برای هر مدیر حساب جدا ساخته شده است (صفحهٔ «مدیران»)، نه یک رمز مشترک.

## ۹. عیب‌یابی

| نشانه                                               | کجا را ببینید و چه کنید                                                                                                                                                                                                        |
| --------------------------------------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------ |
| سرویسی روشن نمی‌ماند                                | `journalctl -u lulu-api -n 50`. اگر نوشته `Invalid environment`، متغیری که نامش آمده را در `.env` درست کنید. اگر `ECONNREFUSED 127.0.0.1:5432` است، دیتابیس بالا نیست: `sudo docker compose up -d`                             |
| پنل باز نمی‌شود و مرورگر خطای گواهی یا اتصال می‌دهد | `journalctl -u caddy -n 50`. دامنه باید به IP سرور اشاره کند (`nslookup <دامنه>`) و پورت ۸۰ و ۴۴۳ باز باشد (`sudo ufw status`)                                                                                                 |
| صفحه «502» یا «Bad Gateway» می‌دهد                  | Caddy بالاست ولی API نه: `systemctl status lulu-api`                                                                                                                                                                           |
| ربات جواب نمی‌دهد                                   | `journalctl -u lulu-bot -n 50` باید `telegram webhook registered` داشته باشد. اگر ربات همین توکن جای دیگری روشن است، خاموشش کنید و `sudo systemctl restart lulu-bot`. در پنل، صفحهٔ «سیستم» وضعیت ربات و worker را نشان می‌دهد |
| ربات پیام را می‌گیرد ولی جواب دیر یا هیچ نمی‌رسد    | worker: `journalctl -u lulu-worker -n 50` و صفحهٔ «سیستم» ← صف ارسال. پیام ناموفق را از همان صفحه دوباره بفرستید                                                                                                               |
| ورود به پنل «تلاش‌های ناموفق زیاد بود» می‌گوید      | چند دقیقه صبر کنید؛ زمان انتظار در خود پیام آمده است. اگر رمز را فراموش کرده‌اید، مالک دیگر از صفحهٔ «مدیران» رمز تازه می‌گذارد. اگر تنها مالک هستید: `docs/panel.md`، «رمز مالک را فراموش کرده‌ام»                            |
| دیسک پر شده است                                     | `df -h`. بیشتر جا مال بکاپ‌ها و لاگ‌هاست: `sudo du -sh /var/backups/lulu /var/log/journal`. لاگ قدیمی: `sudo journalctl --vacuum-time=14d`                                                                                     |
